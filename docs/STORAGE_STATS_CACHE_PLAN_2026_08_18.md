# Storage Statistics Cache Plan

Updated: 2026-08-18

This document defines the production rule for course storage statistics in the
OSSD Course Portal. The goal is to keep the admin dashboard fast while still
providing reliable storage numbers for uploaded courses, temporary upload
space, and course-size ranking.

## 1. Problem

The admin dashboard should not recursively scan the whole course root on every
page load.

The production course root contains many courses, iSpring packages, H5P files,
videos, generated HTML, and Moodle-localized activity files. A full directory
walk can touch tens of thousands of files. Doing that during a dashboard request
causes slow "reading" states and makes the page feel blocked.

Current direction:

1. Dashboard default view must be lightweight.
2. Expensive recursive size scans must run only on explicit refresh, scheduled
   maintenance, or after import/delete operations where the changed course is
   known.
3. Storage numbers shown in the dashboard should be cached with a timestamp and
   a clear freshness state.

## 2. Mature Industry Pattern

Use an indexed/cache-backed model, not request-time filesystem scans.

1. Read realtime disk capacity with `df` or equivalent. This is cheap.
2. Read course-level sizes from a persisted storage index. This is fast.
3. Update the index when known write operations happen:
   - course package import succeeds
   - course replace succeeds
   - course archive/delete succeeds
   - admin temporary upload cleanup succeeds
4. Rebuild the index with a background full scan only when needed:
   - first deployment after adding the feature
   - manual "rescan storage" button
   - nightly scheduled maintenance
   - cache corruption or missing cache

Do not require exact second-by-second course-size accuracy in the default admin
dashboard. Show the cache timestamp and provide a manual rescan path.

## 3. Source of Truth

### 3.1 Realtime Values

These can be read directly on every dashboard request:

- Disk total bytes.
- Disk used bytes.
- Disk free bytes.
- Current configured paths:
  - `COURSE_ACTIVE_ROOT`
  - `COURSE_ARCHIVE_ROOT`
  - `PORTAL_DATA_DIR`

### 3.2 Cached Values

These should come from the storage index:

- Per-course active directory bytes.
- Per-course admin temporary upload bytes.
- Per-course archive bytes.
- Total active course root bytes.
- Total archive root bytes.
- Total admin temporary upload bytes.
- Largest courses ranking.
- Active directory course count.
- Extra active directory course count.

### 3.3 Completion Values

"Online completed courses" must not be derived from storage size.

Use readiness/displayability:

- The course is in the production catalog.
- `course-manifest.json` exists in the current production `COURSE_ACTIVE_ROOT`.
- The manifest parses.
- The manifest contains displayable content such as units, lessons, book
  sections, resources, iSpring, videos, texts, or course downloads.

This is separate from storage accounting.

## 4. Cache Location

Use `PORTAL_DATA_DIR` instead of the project directory, because the cache is
runtime state.

Recommended file:

```text
<PORTAL_DATA_DIR>/storage-overview-cache.json
```

Production example:

```text
/www/wwwroot/ossd-portal/data/storage-overview-cache.json
```

Do not store this cache in `deployment/`, because deployment reports are noisy
and are often generated by scripts. Do not commit the production cache to Git.

## 5. Cache Schema

Recommended shape:

```json
{
  "version": 1,
  "generatedAt": "2026-08-18T03:35:00.000Z",
  "updatedAt": "2026-08-18T03:35:00.000Z",
  "activeRoot": "/www/wwwroot/ossd-portal/courseware-active",
  "archiveRoot": "/www/wwwroot/ossd-portal/courseware-archive",
  "summary": {
    "courseCount": 56,
    "activeDirectoryCourses": 56,
    "extraActiveDirectoryCourses": 1,
    "activeRootBytes": 123456789,
    "archiveRootBytes": 0,
    "adminUploadBytes": 0,
    "courseTotalBytes": 123456789
  },
  "courses": [
    {
      "course": "ENG3U",
      "title": "English, Grade 11, University",
      "status": "active",
      "activeBytes": 123456,
      "adminUploadBytes": 0,
      "archiveBytes": 0,
      "totalBytes": 123456,
      "manifestExists": true,
      "lastScannedAt": "2026-08-18T03:35:00.000Z",
      "source": "full-scan"
    }
  ],
  "warnings": []
}
```

Rules:

1. `version` must increment if schema changes.
2. `activeRoot` and `archiveRoot` must match current env. If they do not match,
   ignore the cache and request a rebuild.
3. Each course record should include `lastScannedAt` and `source`.
4. A missing cache should not break the dashboard. Show realtime disk stats and
   a "storage index not built" message.

## 6. Update Rules

### 6.1 Full Rebuild

Full rebuild scans:

- All catalog courses.
- All active course directories.
- Archive files/directories.
- Admin upload temporary directories.

It writes the complete cache atomically:

1. Build data in memory.
2. Write to `storage-overview-cache.json.tmp`.
3. Rename tmp file to `storage-overview-cache.json`.

Full rebuild should be triggered by:

- Manual "rebuild storage index" button.
- CLI command.
- First deployment/migration.
- Scheduled maintenance.

### 6.2 Course Increment

When a course package import or replace succeeds:

1. Recalculate only that course:
   - `COURSE_ACTIVE_ROOT/<COURSE>`
   - `COURSE_ACTIVE_ROOT/<COURSE>/_admin_uploads`
   - matching archive paths
2. Replace that course record in the cache.
3. Recompute summary totals from cached course records.
4. Update `updatedAt`.

This should run after the import is finalized and after the manifest has been
written. It should not run before finalization, because staging files can inflate
the number.

### 6.3 Course Delete or Archive

When a course is deleted, archived, or cleaned:

1. Recalculate that course if the directory remains.
2. If the active directory no longer exists, set `activeBytes = 0`.
3. Recalculate archive bytes if applicable.
4. Recompute summary totals.

### 6.4 Temporary Upload Cleanup

When admin temporary upload cleanup succeeds:

1. Recalculate `_admin_uploads` only for the affected course, if possible.
2. If cleanup is global, recalculate all admin upload roots or run a full cache
   rebuild in the background.

### 6.5 OSS/CDN Uploads

OSS/CDN storage should not be mixed into ECS course-root size.

The course storage cache covers local ECS paths. If OSS storage is needed, keep
it as a separate cache section, because OSS listing is network-bound and has a
different consistency model.

## 7. API Rules

### 7.1 Default Dashboard

Default dashboard should call a lightweight endpoint:

```text
GET /api/admin/storage?summary=1
```

Expected behavior:

1. Read realtime disk stats.
2. Read storage cache if available.
3. Do not recursively scan all courses.
4. Return `summary.lightweight = true`.
5. Include cache freshness metadata.

### 7.2 Full Storage View

The storage panel can request the full view:

```text
GET /api/admin/storage
```

This can either:

1. Return the cached full index immediately, or
2. Trigger/offer a rebuild if the cache is missing/stale.

It should not silently do a long full scan on every request once the cache
feature exists.

### 7.3 Manual Rebuild

Recommended endpoint:

```text
POST /api/admin/storage/rebuild
```

Expected response:

```json
{
  "ok": true,
  "job": {
    "id": "storage-rebuild-...",
    "status": "queued"
  }
}
```

The rebuild should be a background job if production directories are large.

### 7.4 Recalculate One Course

Recommended internal function and optional endpoint:

```text
recalculateCourseStorage(course)
POST /api/admin/storage/course/<COURSE>/refresh
```

Use this after course import/replace/delete. The endpoint is useful for manual
repair, but normal updates should be called internally by import jobs.

## 8. Concurrency and Safety

1. Use a storage-cache lock or reuse course operation locks for course-level
   recalculation.
2. Do not allow two full rebuilds at the same time.
3. A course-level recalculation may run while another course is importing, but
   should avoid the course currently being replaced.
4. Full rebuild should skip active staging directories unless explicitly
   included.
5. Cache writes must be atomic.
6. If cache write fails, keep serving the previous cache.

## 9. Dashboard Display Rules

Default admin dashboard should show:

- Realtime disk capacity.
- Online completed courses from readiness/displayability.
- Catalog course count.
- Import/display gaps.
- Cached course storage total.
- Cache timestamp.
- A clear button to open full storage view.

Example labels:

```text
Storage cache updated: 2026-08-18 11:35
Course directory size: 289 GB (cached)
Click "View storage" to rebuild or inspect exact course ranking.
```

If cache is missing:

```text
Storage index has not been built yet. Disk capacity is realtime; course-size
ranking requires a storage rebuild.
```

Do not show a long "reading..." state for optional course-size ranking on the
default dashboard.

## 10. Migration Plan

### Phase 1: Lightweight Dashboard

Already started:

1. Default dashboard uses `GET /api/admin/storage?summary=1`.
2. The default view no longer triggers full recursive course-size ranking.
3. The full storage panel still provides the detailed view.

### Phase 2: Cache File and Full Rebuild

Implement:

1. `readStorageOverviewCache()`.
2. `writeStorageOverviewCache(cache)`.
3. `rebuildStorageOverviewCache()`.
4. `POST /api/admin/storage/rebuild`.
5. CLI script:

```text
node scripts/rebuild-storage-overview-cache.mjs --apply
```

Run once on production to backfill historical courses.

### Phase 3: Incremental Updates

Call `recalculateCourseStorage(course)` after:

1. Hybrid/raw course import success.
2. Course package replace/commit success.
3. Course cleanup success.
4. Course archive/delete success.

### Phase 4: Scheduled Maintenance

Optional but recommended:

1. Nightly full rebuild.
2. Keep last successful cache if rebuild fails.
3. Show stale warning when cache is older than 24 hours.

## 11. Verification Checklist

After implementation:

1. Dashboard loads without waiting for course-size scan.
2. `GET /api/admin/storage?summary=1` returns quickly.
3. `GET /api/admin/storage` returns cached detail or a clear rebuild status.
4. Manual rebuild creates `storage-overview-cache.json`.
5. Importing one course updates only that course's storage record.
6. Deleting or replacing one course updates totals correctly.
7. Cache path changes are detected when `COURSE_ACTIVE_ROOT` changes.
8. Online completed course count remains based on readiness/displayability, not
   file size.

## 12. What Not To Do

1. Do not run `directorySize(courseActiveRoot)` on every dashboard load.
2. Do not treat local development course directories as production completed
   courses.
3. Do not mix OSS/CDN byte counts into ECS local course root size.
4. Do not commit production cache files to Git.
5. Do not delete old course roots just to make statistics faster.
